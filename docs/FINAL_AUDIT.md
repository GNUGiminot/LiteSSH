# Финальный аудит: что из присланного промпта внедрять, а где остановиться

Роль: Lead Engineer / Architect. Ниже — честная оценка присланного ТЗ-шаблона (референсы WindTerm /
MobaXterm / SecureCRT) применительно к **реальному** проекту LiteSSH, а не к абстрактному C++/Qt-клиенту
из плейсхолдеров. Вывод: **проект пора замораживать по фичам**. Большинство запрошенного уже сделано,
а оставшееся — либо хрупкое, либо scope-creep с низким ROI. Разбор по модулям + вердикт по каждому.

## Аудит «болей» (из шаблона) против факта

| Боль из шаблона | Статус в LiteSSH |
|---|---|
| Тормозит при `cat huge.log` | Решено: батчинг вывода в main (~8 мс coalescing) + WebGL-рендер xterm + scrollback cap |
| Нет встроенного файлового менеджера | Есть: двухпанельный SFTP (TC-style) + drag&drop + предпросмотр/правка + mc-панель F-клавиш |
| Неудобное управление сессиями | Есть: SQLite-сессии, папки, теги, поиск, шаблоны, импорт ~/.ssh/config, ProxyJump-цепочки |

Плейсхолдер стека в шаблоне (C++/Qt/Rust) не соответствует проекту — здесь Electron + React + TS +
ssh2. Поэтому советы «перепишите рендер на нативный» неприменимы: потолок производительности задан
Electron осознанно (ради скорости разработки и зрелости ssh2/xterm) — см. PROMPT_REVIEW.md.

## Модуль 1 — SFTP и синхронизация с терминалом

**Что уже есть:** две панели (локально ↔ сервер), drag&drop из ОС, рекурсивные передачи с докачкой
(resume), правка файлов на сервере (читаем/пишем прямо по SFTP — **temp-кэш не нужен**, в отличие от
подхода из ТЗ), предпросмотр (CodeMirror/изображения/hex), контекстное меню, mc-панель F3–F8.

**Единственное реально отсутствующее — синхронизация `cd` терминала с деревом SFTP.**

Архитектурный разбор (почему это ловушка):
- Парсить `cd` из потока терминала — то же болото, что и «история команд по нажатиям»: ломается на
  алиасах, `pushd`, subshell, `&&`, автодополнении. Ненадёжно by design.
- **Правильный способ** — не парсинг, а OSC 7: шелл сообщает текущий каталог управляющей
  последовательностью `\033]7;file://host/path\007` (bash/zsh через `PROMPT_COMMAND`, WSL/большинство
  дистрибутивов уже так делают для терминалов). Клиент ловит OSC 7 в потоке и обновляет SFTP-панель.
  ```
  // main: в wireShellStream перехватывать ESC]7;file://…BEL, эмитить cwd в renderer
  const m = chunk.match(/\x1b\]7;file:\/\/[^/]*(\/[^\x07\x1b]*)/)
  if (m) win.webContents.send('term:cwd', termId, decodeURIComponent(m[1]))
  ```
- **Подводные камни:** требует, чтобы у пользователя на сервере был настроен `PROMPT_COMMAND`
  (не гарантировано); OSC 7 приходит вперемешку с данными — нельзя ломать батчинг; путь надо
  URL-декодировать и отфильтровать хост. Двусторонняя синхронизация (клик в SFTP → `cd` в терминал)
  проще (шлём `cd '<path>'\n`), но «загрязняет» историю команды.

**Вердикт: НЕ внедрять в финал.** Ценность нишевая, надёжность зависит от конфигурации чужого сервера,
а поддержка — постоянная. Если очень захочется — только приём OSC 7 (одностороннее подсвечивание cwd),
без парсинга `cd`, и строго как опция. Это единственный кандидат из модуля, и он необязателен.

## Модуль 2 — Производительность и рендеринг

**Что уже есть и почему это правильно:**
- **Разделение потоков сеть/UI**: ssh2 читает сокет в main-процессе; renderer только рисует. Это и есть
  «async I/O + разделение UI-потока» из ТЗ — архитектурно уже так.
- **Буферизация против флуда IPC**: вывод коалесцируется в main окнами ~8 мс (`wireShellStream`), иначе
  `cat` большого файла засыпал бы IPC тысячами мелких сообщений. Это ключевой паттерн — он реализован.
- **Виртуальный скроллинг**: xterm.js сам виртуализирует вывод (рендерит только видимые строки) +
  WebGL-аддон (GPU-рендер, fallback на canvas) + ограничение scrollback (10000 строк).

**Что можно было бы добавить (и почему не нужно):**
- Backpressure/flow-control (притормаживать чтение сокета, если renderer не успевает). На практике
  8-мс-коалесинг уже гасит флуд; настоящий backpressure нужен на потоках в сотни МБ/с, которых по SSH
  почти не бывает. Микрооптимизация с сомнительной отдачей.
- Нативный рендер (как WindTerm) — вне парадигмы Electron, переписывать не будем.

**Вердикт: ГОТОВО.** Архитектура правильная, дальше оптимизировать нечего без смены платформы.
Не трогать — преждевременная оптимизация только добавит багов.

## Модуль 3 — Умные фичи и автоматизация

### Автодополнение по `--help` / `man`
**Вердикт: НЕ внедрять.** Разбор `--help`/`man` вживую — это парсинг произвольного неструктурированного
текста: у каждой утилиты свой формат, флаги в `[]`/`<>`/через запятую, подкоманды, локали. Надёжного
результата нет. Реальные решения (Fig, Warp, Carapace) не парсят `--help`, а тянут **курируемую базу
спецификаций** на тысячи команд — это отдельный продукт, не фича SSH-клиента. Затраты огромные,
надёжность низкая, поддержка бесконечная — классический scope-explosion.
- Что уже закрывает 80% ценности: **сниппеты + история команд** в палитре (Ctrl+Shift+P) с поиском.
  Для «допечатать по истории» этого достаточно.

### Скрипты/макросы
**Вердикт: НЕ внедрять встроенный интерпретатор.** Встраивать Python-движок = большой вес, поверхность
атаки (выполнение произвольного кода), кроссплатформенная возня с рантаймом, бесконечная поддержка API.
- Что уже есть: **многострочные сниппеты = макросы** (сниппет с `\n` выполняется как последовательность),
  плюс синхронный ввод в split-панели. Для «автоматизировать рутину» этого хватает.
- Если однажды понадобится больше — правильный путь не «встроить Python», а «дать пользователю запускать
  ЕГО локальный скрипт, который пишет в сессию» (тонкий мост), а не тащить интерпретатор внутрь.

## Итоговая рекомендация: заморозить фичи на 1.0.1

Проект по ядру (терминал, SFTP, сессии, ключи, туннели, ProxyJump-цепочки, split view, метрики,
безопасность с мастер-паролем, горячие клавиши, mc-панель) **уже соответствует или превосходит**
референсы там, где это осмысленно для персонального кроссплатформенного клиента на Electron.

Оставшиеся пункты из ТЗ — это ровно те места, где начинается «бесконечный пердолинг»:
- **cd↔SFTP-синхронизация** — хрупко, зависит от чужого сервера → максимум опциональный приём OSC 7.
- **`--help`-автокомплит** — отдельный продукт, не фича → пропустить, есть история/сниппеты.
- **встроенные скрипты** — вес и безопасность → пропустить, есть многострочные сниппеты.

**Что делать вместо новых фич (короткий финишный список, по желанию):**
1. Стабилизация: прогон на реальных серверах, фикс найденных багов.
2. Полировка UX уже существующего (пустые состояния, тексты ошибок).
3. Настроить CI-сборку установщика (пункт из PLAN, не фича).

На этом — **стоп по функционалу.** Дальнейшее расширение даёт убывающую отдачу и растит поверхность
багов быстрее, чем ценность. Лучший инженерный ход сейчас — зафиксировать scope и довести качество,
а не добавлять ещё модули.
